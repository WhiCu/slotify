# Отчёт по заданию 1

## 1. Доменная область приложения

**Slotify** — клиент-серверное веб-приложение для бронирования рабочих пространств.

Приложение предназначено для организаций, в которых пользователи бронируют переговорные комнаты и рабочие места. Пользователь может просматривать доступные пространства, выбирать дату и диапазон времени, создавать и отменять собственные бронирования. Администратор управляет пользователями и пространствами.

В приложении используются временные слоты длительностью пять минут. Одни сутки состоят из 288 слотов. Ограничения базы данных не позволяют создать два бронирования одного пространства на одну дату и один временной слот.

Приложение построено по клиент-серверной модели:

- frontend предоставляет пользовательский интерфейс;
- backend реализует бизнес-логику и REST API;
- PostgreSQL хранит данные приложения;

## 3. Основные сущности предметной области

### Пользователь

Пользователь имеет уникальный идентификатор, роль и дату создания. Предусмотрены роли:

- `member` — обычный пользователь;
- `admin` — администратор приложения.

Администратор может создавать и удалять пользователей, просматривать их список и изменять роли.

### Пространство

Пространство имеет идентификатор, название, тип, вместимость, признак активности и дату создания.

Поддерживаются два типа пространств:

- `meeting_room` — переговорная комната;
- `desk` — рабочее место.

Администратор может создавать, изменять, деактивировать и удалять пространства.

### Бронирование

Бронирование связывает пользователя, пространство, дату и временной слот. При создании можно указать диапазон слотов и количество посетителей.

Для бронирований предусмотрены создание, получение отдельной записи, получение списка бронирований текущего пользователя, просмотр занятости пространства и отмена бронирования.

### Данные PostgreSQL

В базе данных используются таблицы:

- `users` — пользователи;
- `spaces` — рабочие пространства;
- `reservations` — отдельные забронированные слоты.

Между таблицами настроены внешние ключи. Для таблицы `reservations` задано уникальное ограничение по полям `space_id`, `date`, `slot`.

## 4. CRUD и REST API

В приложении реализованы CRUD-операции над основными сущностями.

### Пользователи

- `POST /users` — создание пользователя;
- `GET /users` — получение списка пользователей;
- `GET /users/{id}` — получение пользователя по идентификатору;

- `PATCH /users/{id}/role` — изменение роли пользователя;
- `DELETE /users/{id}` — удаление пользователя.

### Пространства

- `POST /spaces` — создание пространства;
- `GET /spaces` — получение списка пространств;
- `GET /spaces/{id}` — получение пространства по идентификатору;

- `PATCH /spaces/{id}` — изменение названия и вместимости;
- `DELETE /spaces/{id}` — удаление пространства;
- `POST /spaces/{id}/deactivate` — деактивация пространства.

### Бронирования

- `POST /bookings` — создание бронирования;
- `GET /bookings/{id}` — получение бронирования;
- `GET /bookings/my` — получение бронирований текущего пользователя;

- `GET /bookings/occupancy` — получение занятых слотов пространства за день;
- `POST /bookings/cancel` — отмена бронирования.

Дополнительно реализован технический endpoint `GET /healthz`, который используется для проверки работоспособности backend-сервиса.

## 5. Соответствие методологии 12 факторов

### I. Codebase — одна кодовая база

Весь исходный код приложения хранится в одном репозитории. Репозиторий содержит frontend, backend, OpenAPI-контракт, SQL-миграции, конфигурацию и Docker Compose-файл.

Одна кодовая база может использоваться в разных окружениях: локальном, тестовом и контейнерном. Отличия между окружениями задаются конфигурацией и переменными окружения, а не изменением исходного кода.

**Соответствие: да.**

### II. Dependencies — явное объявление зависимостей

Зависимости backend явно указаны в `go.mod` и зафиксированы в `go.sum`. Зависимости frontend указаны в `frontend/package.json`.

При сборке контейнеров зависимости устанавливаются средствами соответствующих package manager. Приложение не использует незафиксированные системные библиотеки или зависимости, установленные вручную.

**Соответствие: да.**

### III. Config — конфигурация

Конфигурация приложения вынесена из исходного кода. Используются YAML-файлы и переменные окружения с префиксом `APP_`.

Через конфигурацию задаются:

- параметры HTTP-сервера;
- адрес, порт и учётные данные PostgreSQL;
- параметры пула соединений;
- криптографические ключи;
- параметры логирования;
- настройки OpenTelemetry;
- разрешённые CORS-источники.

При запуске в Docker Compose адреса backing services передаются через переменные окружения. Это позволяет запускать один и тот же образ в разных окружениях.

**Соответствие: да.**

### IV. Backing services — подключаемые внешние сервисы

PostgreSQL и OpenTelemetry Collector рассматриваются как подключаемые внешние сервисы. Они запускаются отдельными контейнерами Docker Compose и подключаются к backend по сетевым адресам.

Backend не содержит встроенную базу данных и не зависит от конкретного локального экземпляра PostgreSQL. При необходимости можно подключить другой экземпляр PostgreSQL, изменив только конфигурацию.

**Соответствие: да.**

### V. Build, release, run — сборка, релиз и запуск

Этапы сборки и запуска разделены.

На этапе build зависимости устанавливаются, а исходный код компилируется. Backend собирается многоэтапным Dockerfile в отдельный бинарный файл. На этапе release формируется контейнерный образ с собранным приложением и конфигурацией. На этапе run контейнер запускает backend и HTTP-сервис frontend.

Миграции PostgreSQL запускаются при старте приложения через флаг `--up-migrate`. Благодаря этому схема базы данных приводится к актуальному состоянию автоматически.

**Соответствие: да.**

### VI. Processes — процессы без общего состояния

Backend работает как stateless HTTP-процесс. Пользовательские данные, пространства и бронирования хранятся в PostgreSQL, а не в памяти или локальных файлах backend.

Аутентификация выполняется по Bearer-токену, поэтому запросы не требуют привязки пользователя к конкретному экземпляру приложения. Это позволяет запускать несколько экземпляров backend.

**Соответствие: да.**

### VII. Port binding — привязка к порту

Backend самостоятельно запускает HTTP-сервер и принимает запросы на порту `8080`. Frontend запускает собственный HTTP-сервер на порту `3000`.

Docker Compose публикует эти порты наружу. Компоненты приложения не требуют отдельного внешнего web-сервера для обработки HTTP-запросов.

**Соответствие: да.**

### VIII. Concurrency — конкурентность

HTTP-сервер Go обрабатывает запросы конкурентно. Приложение может обслуживать несколько пользователей одновременно.

Согласованность операций бронирования обеспечивается PostgreSQL, транзакциями и ограничениями уникальности. Поэтому параллельные попытки занять один и тот же слот не приводят к появлению дублирующих бронирований.

**Соответствие: да.**

### IX. Disposability — быстрое завершение работы

Backend обрабатывает сигналы `SIGINT` и `SIGTERM`, корректно завершает HTTP-сервер и освобождает ресурсы.

Для HTTP-сервера настроены таймауты чтения, записи и простоя, а также ограничение размера запроса. PostgreSQL имеет healthcheck, а backend запускается после готовности базы данных.

Контейнеры можно быстро остановить и перезапустить средствами Docker Compose без потери данных, поскольку данные хранятся в PostgreSQL volume.

**Соответствие: да.**

### X. Dev/prod parity — близость окружений разработки и эксплуатации

В локальном и контейнерном окружении используются один и тот же исходный код, API-контракт, миграции и PostgreSQL. Docker Compose поднимает полный стек приложения: frontend, backend, PostgreSQL и OpenTelemetry Collector.

Команды сборки, запуска, остановки, тестирования и генерации кода вынесены в `taskfile.yaml`, поэтому действия разработчика воспроизводимы.

**Соответствие: да.**

### XI. Logs — логи как поток событий

Backend ведёт структурированные логи с уровнями `debug`, `info`, `warn` и `error`. В логах фиксируются запуск HTTP-сервера, HTTP-запросы, ошибки и результаты прикладных операций.

Для передачи телеметрии используется OpenTelemetry. Логи и трассировки содержат идентификаторы запросов и могут быть переданы в централизованную систему наблюдаемости через OpenTelemetry Collector.

**Соответствие: да.**

### XII. Admin processes — административные процессы

Административные и разовые задачи не являются частью основного цикла обработки HTTP-запросов. Они запускаются отдельными командами и режимами.

В проекте отдельно выполняются:

- миграции PostgreSQL;
- модульные и интеграционные тесты;
- генерация Go-кода по OpenAPI;
- сборка Docker-образов;
- запуск и остановка окружения.

Примеры команд:

```bash

```

### I. Codebase — одна кодовая база, несколько развёртываний

Проект хранится в одном репозитории и содержит исходный код backend, frontend, API-контракт, миграции и конфигурацию запуска. Один и тот же код может использоваться в локальном окружении и в Docker-окружении.

Секреты и локальные значения вынесены в файл `config/.env`, который не должен включаться в архив с исходным кодом. В репозитории должен присутствовать только пример конфигурации без настоящих секретов.

**Статус: соответствует с оговоркой.** Кодовая база единая, однако frontend и backend должны быть окончательно согласованы в production Docker-сценарии.

### II. Dependencies — явное объявление зависимостей

Backend-зависимости зафиксированы в `go.mod` и `go.sum`. Frontend-зависимости зафиксированы в `frontend/package.json`.

Dockerfile устанавливает Go-зависимости через `go mod download`. Для frontend зависимости устанавливаются стандартным Node.js package manager из `package.json`.

**Статус: соответствует.**

### III. Config — конфигурация в окружении

Настройки приложения хранятся в YAML-конфигурации и могут переопределяться переменными окружения с префиксом `APP_`. Через конфигурацию задаются адрес PostgreSQL, параметры HTTP-сервера, криптографические ключи, телеметрия и логирование.

Docker Compose передаёт параметры подключения к PostgreSQL и OpenTelemetry через переменные окружения.

**Статус: в основном соответствует.** Для production необходимо заменить тестовые значения секретов в `config/config.yaml` и передавать их только через защищённое окружение или секрет-хранилище.

### IV. Backing services — внешние сервисы как подключаемые ресурсы

PostgreSQL и OpenTelemetry Collector запускаются как отдельные Docker Compose-сервисы. Backend подключается к PostgreSQL по адресу и параметрам, заданным конфигурацией, поэтому базу данных можно заменить другим экземпляром PostgreSQL без изменения бизнес-логики.

**Статус: соответствует.**

### V. Build, release, run — разделение сборки, релиза и запуска

Backend собирается многоэтапным Dockerfile: сначала выполняется компиляция Go-бинарника, затем бинарник переносится в минимальный runtime-образ distroless. При запуске backend может выполнить миграции PostgreSQL через флаг `--up-migrate`.

Для полного соответствия фактору frontend также должен иметь отдельный production build и отдельный runtime-сценарий. В текущем состоянии Dockerfile описывает backend, а сервис `frontend` в Compose использует тот же Dockerfile. Это требует доработки: например, отдельного frontend Dockerfile или общего multi-stage Dockerfile с корректным запуском Node.js-сервера.

**Статус: частично соответствует.** Backend соответствует, production-сборка frontend требует исправления.

### VI. Processes — приложение выполняется как stateless-процессы

Backend не хранит состояние пользовательских данных в локальной файловой системе. Пользователи, пространства и бронирования хранятся в PostgreSQL. Аутентификация выполняется по Bearer-токену, поэтому экземпляры backend можно масштабировать горизонтально.

**Статус: в основном соответствует.** Логи сейчас дополнительно направляются в файл, поэтому файловое состояние не должно использоваться как источник данных приложения.

### VII. Port binding — экспорт сервисов через порт

Backend запускает HTTP-сервер и публикует порт `8080`. Frontend предполагает запуск собственного HTTP-сервера на порту `3000`, а в Docker Compose этот порт опубликован наружу.

**Статус: частично соответствует.** Backend соответствует. Для frontend необходимо завершить корректную сборку и запуск Node.js-сервера в контейнере, иначе публикация порта `3000` не обеспечивает работающий frontend.

### VIII. Concurrency — масштабирование через процессы и экземпляры

HTTP-сервер Go обслуживает несколько запросов конкурентно. Приложение не привязано к одному пользовательскому процессу или локальной сессии, а данные находятся в PostgreSQL. Docker Compose позволяет запускать сервисы независимо.

**Статус: соответствует для backend.** Для масштабирования бронирований необходимо сохранять уникальные ограничения и транзакционную логику PostgreSQL, что уже предусмотрено схемой базы данных.

### IX. Disposability — быстрая и корректная остановка

Backend обрабатывает системные сигналы `SIGINT` и `SIGTERM` через `signal.NotifyContext`. HTTP-сервер имеет таймауты запросов и ограничения размера запроса. Контейнеры могут быть остановлены средствами Docker Compose.

PostgreSQL получает healthcheck, а backend запускается после готовности базы данных.

**Статус: соответствует.**

### X. Dev/prod parity — близость сред разработки и production

Локальный запуск и контейнерный запуск используют один backend-код, те же миграции и PostgreSQL. Docker Compose поднимает инфраструктуру, близкую к production-сценарию: приложение, PostgreSQL и OpenTelemetry Collector.

**Статус: частично соответствует.** Среды backend близки, но frontend должен использовать единый проверенный сценарий сборки и запуска как локально, так и в контейнере.

### XI. Logs — логи как поток событий

Backend использует логирование HTTP-запросов и отдельный logger с уровнями логирования. В проекте также подключена интеграция с OpenTelemetry для передачи телеметрии.

**Статус: частично соответствует.** Приложение пишет логи в файл `logs/app.log`, что удобно для локальной разработки, но для строгого соответствия 12 фактору в production предпочтительнее направлять логи в `stdout`/`stderr`, а агрегацию выполнять на уровне Docker или внешней платформы.

### XII. Admin processes — административные задачи как одноразовые процессы

Миграции базы данных реализованы через Goose и могут запускаться отдельным административным режимом при старте backend с флагом `--up-migrate`. Проверки, тесты и генерация кода вынесены в отдельные Taskfile-команды.

Примеры команд:

- `task test` — запуск тестов;
- `task generate` — генерация кода;
- `task docker:build` — сборка Docker-образов;
- `task docker:up` — запуск окружения;
- `task docker:down` — остановка окружения.

**Статус: соответствует.**

## 7. Запуск приложения

Для запуска инфраструктуры используется Docker Compose:

```bash
task docker:build
task docker:up
```

Backend доступен на `http://localhost:8080`, PostgreSQL — на порту `5432`, OpenTelemetry Collector принимает OTLP gRPC на порту `4317`.

Frontend в режиме разработки запускается из директории `frontend`:

```bash
npm install
npm run dev
```

Перед запуском необходимо настроить переменные окружения и убедиться, что зависимости frontend установлены.

## 8. Проверка проекта

Backend покрыт модульными и интеграционными тестами. Команда `go test ./...` проверяет компиляцию пакетов и выполнение доступных тестов.

Основные проверки приложения:

- проверка подключения к PostgreSQL;
- выполнение миграций;
- тестирование доменных правил;
- проверка репозиториев и конфигурации;
- проверка HTTP API через OpenAPI-контракт.
